# 灵境技术栈蓝图（2026-09-09 用户拍板）

> 定位：选择编程语言"不应看作选一个，而应看作设计多语言协同的技术栈"。
> 本文件是**目标架构**记录，并给出分阶段采用路线与对现有 JS 原型的定位。

## 一、目标技术栈（多语言协同）

| 语言 | 角色 | 承担 |
|---|---|---|
| **C++** | 物理与渲染基石 | 3D PDE 数值（热/波/泊松/平流扩散）、实时渲染、确定性仿真内核 |
| **Python** | AI 与算法大脑 | LLM 编排（OpenRouter）、ROM/POD 数值、降阶、教学关系 R_教学、价值函数 V(s) |
| **Go** | 网络与数据骨架 | 多人在线、并发会话、API 网关、持久存储与分片/共识 |

设计意图：核心体验靠 C++ 保性能，AI/算法靠 Python 快开发，系统扩展靠 Go 扛并发——三者各司其职。

## 二、务实判断（独立工程视角，敢反对）

- ✅ **长期成立**：真实 3D 物理+渲染要吃 C++ 性能；AI 编排与数值（numpy/scipy、POD/SVD）Python 生态最省；多人在线 Go 的 goroutine 并发模型最合适。
- ⚠️ **当前阶段直接铺三运行时 = 过早基建**：
  - 三套工具链 + FFI/grpc 互操作边界 + 三运行时部署调试，对单人非码农是沉重负担；
  - 上轮 JS 原型已端到端跑通框架（world/physics/rom/teaching + `node index.js` 全断言过），验证的是"数学与确定性对不对"，不是"语言对不对"；
  - 教师 MVP 的**真实风险是产品留存/付费意愿**，不是性能或并发——这部分用原型即可验，不必先付三运行时税。
- 建议：蓝图作为**目标架构**锁定，但按产品信号**分阶段采用**，不在验证产品前承担三运行时的基础设施税。

## 三、分阶段采用（最小可执行切片）

- **P0（现在）JS 原型**：跑通框架 + 验证教师 MVP。定位 = **原型 / 参考实现**，非目标栈。
- **P1（AI 脑）迁 Python**：把算法/AI 层迁 Python（ROM/POD 数值 + LLM 编排最自然、风险最低、直接复用 numpy/scipy）。
- **P2（性能）迁 C++**：仅当真实 3D / 实时渲染成为瓶颈时，把物理 PDE 内核迁 C++。
- **P3（规模）迁 Go**：仅当真实多人在线（分片+共识/CRDT）上线时，把网络/数据骨架迁 Go。

## 四、与现有 JS 实现的关系

- `world.js` / `physics.js` / `rom.js` / `teaching.js` / `index.js` = 原型/参考实现，验证数学正确性与确定性并发合并；目标栈落地后可作为**规格与跨语言回归基准**。
- 未来互操作边界：Python↔C++ 用 pybind11 / gRPC；Go↔其余用 gRPC / msgpack；世界状态用确定性序列化（`world.js` 的 JSON 快照可作跨语言契约雏形）。
- 诚实标注不变：①"全息对偶"是 ROM 压缩隐喻，非字面 AdS/CFT（物理猜想）；② 哥德尔不完备不进代码。
