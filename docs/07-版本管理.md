# 07 · 版本管理

> 灵境目前**没有版本号体系**。这篇文档说明现状、为什么，以及建议的约定 —— 现状与约定分开写，避免把"打算"当成"已有"。

---

## 一、现状（事实）

| 项 | 现状 |
|---|---|
| `package.json` | **没有**。仓库不使用 npm 分发，无版本字段 |
| 版本号 | **无**。历史文档里出现过 `v1.1.0 / v1.2.0` 字样（PRD、技术设计），那是文档自身的版本，**不是产品版本**，且已随文档归档 |
| Git 标签 | 仅两个：`v1.0.0`、`pre-rewrite-20260909`（前者为早期定位，后者标记 2026-09-09 方向推翻前的存档点） |
| GitHub Releases | **无** |
| CI | **无**。没有任何自动化检查在看仓库 |
| 分支 | 单支 `main` |
| 提交数 | 43（2026-09-04 首提交 → 2026-09-16 最后一次已提交改动） |
| 发布渠道 | 无。仓库即"自托管发布"：使用者 clone 后自行运行 |

**为什么没有版本号**：产品形态在 2026-09-09 被整段推翻、09-11 又删除了一层自动判定。在定位剧烈变化期给版本号，只会让编号与语义脱节。定位稳定后再启用版本号更诚实。

---

## 二、当前如何表达"这一版是什么"

因为没版本号，实际靠三样东西对齐：

1. **Git 提交 SHA**（`git log -1 --format=%h`）——对外沟通时以它为准。
2. **文档里的"诚实说明"日期段**——例如"2026-09-11 重大变更：移除自动判定层"。每次语义级变化，在相关文档留下带日期的说明段，而不是改版本号。
3. **测试真实基线**——见 [02 · 使用指南](02-使用指南.md#五测试与真实基线)。文档里的数字必须能在本机复跑出来。

---

## 三、建议约定（尚未启用，待定位稳定后由维护者决定）

若日后启用版本号，建议：

- **`MAJOR.MINOR.PATCH`**
  - `MAJOR`：世界模型 / 角色契约变化（例如新增或删除"判定权"相关边）—— 这类变化属于**契约破坏**，任何依赖方都须复核。
  - `MINOR`：新增探测策略 / 新增模块 / 新增提供商等向后兼容的能力扩展。
  - `PATCH`：文案、兜底语料、注释、测试补充。
- **标签格式**：`vX.Y.Z`；方向性推翻另打 `pre-<方向>-<日期>` 存档标签（沿用 `pre-rewrite-20260909` 的先例）。
- **发布一致性清单**（每次发布前逐条过）：

| # | 检查项 | 为什么 |
|---|---|---|
| 1 | README / docs 里的**工具数与能力清单**与实际代码一致 | 历史上有过一次"文档写着已实现、代码里是停用占位" |
| 2 | docs 里的**测试数字**与本次真实跑出的数字一致 | 数字不能猜 |
| 3 | 已删除的假理论**没有在任何文档里复活** | `P(t)` / `E(t)` / `σ²` 及其衍生指标 |
| 4 | `git status` 干净、`main` 与 `origin/main` 一致 | 避免"本地看起来已发布、远端没有" |
| 5 | 密钥扫描：仓库内无任何 `LINGJING_*_KEY` 明文 | 密钥只允许在服务端环境变量 |
| 6 | 新增功能先证"深化了盲区照见反思环" | 见 [03](03-设计思想.md#六防漂移红线改代码前先读这一节) 防漂移红线 |

## 四、兼容性承诺（当前）

| 面 | 承诺 |
|---|---|
| **HTTP 接口** | 无稳定承诺。`/api/class/start`、`/api/class/reply` 等为内部接口，可能变 |
| **落盘格式** | `sessions/*-world.json`、`retention.jsonl` 为内部格式，**不承诺向后兼容**；升级后建议重新跑课 |
| **环境变量名** | `LINGJING_*` 前缀视为稳定；改名会走文档说明 |
| **代码 API** | `teacher.js` / `teaching.js` / `questioning.js` / `reflection.js` 的导出为内部 API，不承诺稳定 |

一句话：**这是一个还在成形的自托管项目，不是提供稳定 API 的产品。**
